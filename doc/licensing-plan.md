# SDK 라이선스·신청 절차 개편안

2026-10-16 작성, 같은 날 결정 확정. **구현 전 문서다.** 현재 적용 정책은 [entitlement.md](entitlement.md),
[LICENSE](../LICENSE), [policy-history.md](policy-history.md)에 있고, 이 문서의 내용은 구현을 거쳐 그쪽에 반영한다.
결정 내역은 [11절](#11-결정-사항)에 있다.

## 0. 요약

- SDK는 **완전히 막지 않는다.** **전체 모드**와 **기본 모드**로 기능을 나눈다.
- **14일 체험(전체 모드)은 상업·비상업 구분 없이** 누구나 신청한다. 상업 체험은 신청자 정보를 함께 입력한다. 체험도 **담당자가 확인한 뒤 승인**하며, 승인한 날부터 14일이다.
- 체험이 끝나면 **기본 모드**(기간 제한 없음). 정품 장비 구매에 포함된 기본 사용권이 이 범위다.
- 비상업 연구·교육은 **관리자가 승인과 기간을 정하는 무료 연장**을 받을 수 있다.
- 상업은 체험 이후 **별도 계약이 있어야만** 전체 모드를 쓴다. 계약 종료 후 30일 유예, 그다음 기본 모드.
- **SDK 키 = 좌석.** 계약(체험 포함)마다 좌석 수만큼 키를 만든다. 키는 처음 쓸 때 인증해 **앱 ID(모바일·macOS 앱) 또는 PC(Windows·Python 등)에 묶인다.**
- 키 **유효기간은 발급할 때 사용자가 고른다**(30일·90일·1년·만료 없음). 같은 키로 갱신한다(온라인 자동, 오프라인은 포털 파일).
- 판정과 기능 제한은 **비공개 코어 안**에서 한다. 서버는 키가 어디에 묶였는지만 알고, 측정 횟수나 사용 시각은 모른다.

## 1. 배경과 목표

현재(2026-10-14 정책):

- 기본 사용권은 항상 `granted`이고, 키(확인 정보)는 회사·계약을 **경고로만** 알려준다. 어떤 상태도 기능을 막지 않는다.
- 키는 앱이나 기기에 묶이지 않는다. 진짜 키를 다른 앱에 넣으면 원래 회사·계약으로 표시된다.
- 키 없이도 모든 기능을 쓸 수 있어 상업 계약으로 이어질 동기가 약하다.
- 공개 PyPI `fisica` 1.0.0·1.0.1(MIT)에 1세대 프로토콜 파서와 발 크기 분석이 공개돼 있다(삭제 예정, W6).

목표:

- 키 없이도 장비의 기본 기능은 계속 쓴다(기본 사용권 유지).
- 제품·서비스에 필요한 기능은 체험 또는 계약이 있을 때만 쓴다.
- 체험에서 상업 계약으로 자연스럽게 이어지게 한다.
- 키를 앱·PC 단위 좌석으로 관리해 복사·공유를 막는다.
- 인터넷이 없는 현장(키오스크·병원 폐쇄망)에서도 키 기한 안에는 동작한다.

비목표:

- DRM 수준의 복제 방지. 코어 바이너리 패치, SDK 없이 프로토콜 직접 구현은 SDK만으로 막을 수 없다(7절).
- 사용량 추적. 측정 횟수·사용 시각은 수집하지 않는다(8절).

## 2. 라이선스 모드

### 2.1 모드

| 모드 | 언제 | 기간 |
|---|---|---|
| **전체 모드** | 사용 중인 키(현재 앱·PC에 묶이고 키 기한 안)이고, 그 계약(체험·연장·상업 계약)이 전체 모드 기간 안 | 키 기한과 계약 전체 모드 종료 중 이른 쪽까지 |
| **기본 모드** | 키 없음, 미활성 키, 다른 앱·PC, 키 만료·해제, 체험 종료, 계약 만료(유예 후)·폐기, 서명 실패, 시계 되돌림 | 제한 없음 |

| 기능 | 전체 | 기본 | 비고 |
|---|---|---|---|
| 검색·연결·해제, 재연결 후 측정 재개 | O | O | |
| 측정 시작·종료, 기간 지정 | O | O | |
| 배터리 잔량, 기기 정보 | O | O | |
| 기기 설정·영점·보정 | O | O | 안전·유지보수 기능은 막지 않는다 |
| 체중 | O | O | |
| 발 길이·폭 | O | O | 이미 MIT 1.0.x에 공개된 수준 |
| 실시간 압력 미리보기(표시용 29×29 격자) | O | 제한 | 기본 모드는 초당 1장(2026-10-17 확정. 기기 기본 속도는 초당 약 3장) |
| 원본 패킷(645바이트), 원본 격자(29×22), 가공 격자 | O | X | 자체 분석·제품화의 핵심 |
| 보고서 내보내기(JSON 등) | O | 요약만 | 기본 모드는 체중·발 길이·폭 요약만, 프레임 없이(2026-10-17 확정) |
| 향후 고급 분석(보행·자세 지표 등) | O | X | 계약 차별화 |

- 막힌 기능은 오류 코드 `FEATURE_NOT_LICENSED`(가칭)와 이유를 돌려준다. 측정·통신 오류와는 구분한다.
- **Mock(기기 없는 합성 데이터)도 같은 규칙**을 따른다(D6). 키 없이는 기본 기능만, 전체 기능은 체험 키로.

### 2.3 판정 순서 (코어)

1. 서명된 키가 있고 서명이 유효한가? 아니면 기본 모드(`unverified`).
2. 키가 활성화돼 있는가(`bind`가 있는가)? 아니면 기본 모드(`not_activated`).
3. 키의 `bind`가 현재 앱 ID 또는 PC 해시와 같은가? 아니면 기본 모드(`bind_mismatch`).
4. 계약 폐기나 키 해제가 서명돼 있는가(`revoked_at`)? 있으면 기본 모드(`revoked`).
5. 현재 시각이 지금까지 본 가장 늦은 시각이나 키의 `verified_at`보다 1시간 넘게 이른가? 이르면 기본 모드(`clock_rollback`, D8). 1시간 안의 되돌림(시계 보정)은 허용한다.
6. `key_until`이 있고 지났는가? 지났으면 기본 모드(`key_expired`). 온라인이면 SDK가 먼저 갱신을 시도한다.
7. `full_until`이 지났는가? 지났으면 기본 모드(`expired`). 계약 종료일은 지났지만 `full_until` 전이면 유예 경고(`grace`).
8. 모두 통과하면 전체 모드. `features`가 있으면 그 기능만 전체로 연다.

상태 API는 모드, 이유, 키 기한, 전체 모드 종료 시각, 남은 유예 일수를 돌려준다.

### 2.4 코어 구조 (W1, 2026-10-17 확정)

- **제한은 코어가 직접 건다(C ABI 2.0).** 래퍼는 소스가 공개라 래퍼에서 거는 제한은 한 줄로 풀린다.
  - 세션이 측정 패킷을 직접 해석해 모드에 맞는 데이터만 넘긴다. 기본 모드는 원본 패킷·원본 격자 없이 표시용 격자와 체중을 초당 1장까지만 넘긴다.
  - 발 길이·폭은 세션이 받은 모든 패킷으로 코어가 계산한다(기본 모드도 같은 품질).
  - 원본·가공 격자를 돌려주는 해석 함수(`decode_packet`, `preprocess`, `display_grid`)는 라이선스 컨텍스트를 받아 `raw_data` 기능이 열린 경우에만 동작한다.
  - 한계: 블루투스·USB 바이트는 앱을 거쳐 코어로 들어오므로, 프로토콜을 직접 해석하는 것은 막지 못한다(7절 "SDK 없이 프로토콜 직접 구현"과 같은 위험).
- 대상(앱 ID·PC 해시)은 코어가 읽는다. macOS는 `.app` 번들이고 인터프리터(`org.python.python`, `com.apple.*`)가 아니면 앱 ID, 아니면 `gethostuuid()`(IOPlatformUUID와 같은 값)로 만든 PC 해시.
- 시계 되돌림 허용 오차는 1시간. 지금까지 본 가장 늦은 시각은 상태 파일에 함께 저장한다.
- 보고서 내보내기는 래퍼가 상태의 기능 비트를 보고 정한다. 기본 모드는 요약만(체중·발 길이·폭).
- 아직 배포한 패키지가 없어 ABI 1.x 호환은 두지 않는다. 코어 2.0.0, SDK 3.0.0.

## 3. 사용자 유형별 경로

```
체험 신청 → 담당자 승인 (승인일부터 14일, 전체 모드) ── 누구나. 계정·회사·사업자번호·앱 ID·PC당 1회
├─ 비상업: Fisica 개인 계정 → 신청 → 승인 (좌석 3)
└─ 상업:   Fisica Pro 계정 → 신청자 정보 → 신청 → 승인 (좌석 5)
           반려·철회된 신청은 다시 할 수 있음

체험 종료 → 기본 모드
├─ 비상업: 연구·교육 연장 신청 → 관리자가 승인·기간·좌석 결정 → 무료 전체 모드
└─ 상업:   계약 신청 → 관리자 검토 → 계약(기간·좌석·기능·최대 키 기한) → 전체 모드
           계약 없이는 체험 이후 전체 모드 없음
           계약 종료 → 30일 유예 → 기본 모드
```

## 4. 신청과 키 관리 (포털)

### 4.1 비상업 체험

1. "무료 체험 신청" → Fisica 개인 계정(B2C)으로 로그인 또는 가입.
2. 기본 약관 동의.
3. 사용 목적(교육·연구·도입 검토·개인·공공), 프로젝트 이름과 설명, 대상 플랫폼.
4. 신청이 "검토 중"으로 접수된다. 담당자가 확인하고 승인하면(4.2a) 그날부터 체험이 시작된다(좌석 3).
   대시보드에 남은 체험 일수를 표시하고, 이어서 키를 만든다(4.5).

### 4.2 상업 체험

1. "무료 체험 신청(상업)" → Fisica Pro 계정(B2B)으로 로그인.
2. 기본 약관 동의.
3. 신청자 정보:

| 항목 | 출처 | 필수 |
|---|---|---|
| 회사명, 사업자등록번호, 업종 | Fisica Pro 계정에서 자동 (`Organization`) | 자동 |
| 담당자 이름·직함·전화·이메일 | 새로 입력 | 필수 |
| 제품·서비스명, 설명 | 신청서 기존 항목 | 필수 |
| 사용 형태(자사 시설/자사 앱/납품·SI/OEM) | 신청서 기존 항목 | 필수 |
| 대상 플랫폼, 예상 기기 수, 웹사이트 | 신청서 기존 항목 | 선택 |
| 도입 예정 시기 | 새로 입력 | 선택 |
| 개인정보 수집·이용 동의 | 새로 입력(항목·목적·보유기간 고지) | 필수 |

4. 신청이 "검토 중"으로 접수된다. 담당자가 연락처로 확인하고 승인하면(4.2a) 그날부터 체험이 시작된다(좌석 5).
   승인된 체험은 관리자 화면 "체험 현황"에 표시된다.

### 4.2a 체험 승인 (2026-10-17 변경)

- 상업·비상업 모두 체험은 관리자 승인을 거친다. 관리자 화면 "신청 심사"에 다른 신청과 함께 들어온다.
- 승인할 때 기본값(기간 14일, 좌석 비상업 3·상업 5, 월 이동 상한 1, 기능 전체)을 쓰거나 조정한다. 최대 키 기한도 정할 수 있다.
- 체험 기간은 **승인한 날부터** 센다. 승인 시점에 계정·회사·사업자번호의 체험 사용 기록을 남기고, 이미 쓴 경우 승인이 거절된다.
- 검토 중인 체험 신청이 있으면 새 신청을 받지 않는다. **반려되거나 철회한 신청은 다시 할 수 있다.**
- 보류(나중에 정함): 새 신청 알림, 상담 중 상태와 메모, 신청자 결과 알림.

### 4.3 비상업 연구·교육 연장 (D2)

- 비상업(Fisica 개인 계정)만 신청할 수 있다. 상업 사용은 연장 대상이 아니다.
- 기관명, 과제·수업 설명, 희망 기간, 지도교수·담당자를 받는다.
- **관리자가 결정한다:** 승인 여부, 기간(기본값 1년), 좌석 수(기본값 3), 허용 기능(기본은 전체), 최대 키 기한.
- 만료가 다가오면 다시 신청하고 관리자가 재연장 여부를 정한다. 관리자는 기간 수정과 조기 종료도 할 수 있다.

### 4.4 상업 계약

상업 사용은 14일 체험 이후 **계약이 있어야만** 전체 모드를 쓴다(D5). 무료 연장 경로는 없다.

1. 체험 신청 정보를 이어받은 계약 신청서를 제출한다(재입력 없음).
2. 관리자가 계약을 만든다: 시작·종료일, 좌석 수, 월 이동 상한(기본값 2), 허용 기능, 법적 권한(`grants`: OEM 등), **최대 키 기한**(기본값 제한 없음).
3. 회사가 좌석 수만큼 키를 만든다(4.5). 계약 변경(좌석·기간·기능)은 다음 갱신이나 갱신 파일에 반영된다.
4. 종료 30일 전부터 대시보드·이메일로 갱신을 안내한다.

### 4.5 키(좌석) 관리

**만들기**

- 계약(체험·연장·상업)의 좌석 수까지 만든다. 이름과 **유효기간**(30일·90일·1년·만료 없음)을 고른다.
- 관리자가 계약에 최대 키 기한을 정했으면 그보다 긴 기간은 고를 수 없다(D10).
- "만료 없음"을 고를 때 안내: 오프라인에서 해제를 요청하면 해제 코드나 관리자 해제 없이는 계약이 끝날 때까지 좌석이 묶인다.
- 처음 받은 키는 **미활성** 상태다. 이 상태로는 기본 모드로만 동작한다.

**활성화 (처음 한 번)**

- 온라인: 앱에서 키를 넣으면 SDK가 앱 ID 또는 PC 해시를 서버로 보내 키를 묶고, 묶인 키를 돌려받아 저장한다.
- 오프라인: SDK가 보여주는 **활성화 코드**를 다른 기기로 포털의 그 키에 입력하면, 묶인 키 파일(.fse)을 내려받아 넣는다.
- 이미 다른 앱·PC에 묶인 키는 활성화되지 않는다.

**갱신 (같은 키)**

- 키 기한은 마지막 갱신부터 고른 기간만큼이다.
- 온라인 기기는 SDK가 기한 전에 자동으로 갱신한다(기존 갱신 API).
- 오프라인 기기는 포털에서 같은 키의 **갱신 파일**을 받아 넣는다. 새 좌석도, 이동 횟수도 쓰지 않는다.
- 갱신해도 계약의 전체 모드 기간(체험 14일, 계약 종료+유예)을 넘지 않는다.

**키 상태**

| 상태 | 뜻 | 좌석 | 사용자가 할 수 있는 일 |
|---|---|---|---|
| 미활성 | 만들었지만 아직 앱·PC에 묶이지 않음 | 차지 | 바로 삭제(이동 아님) |
| 사용 중 | 앱·PC에 묶이고 기한 안 | 차지 | 해제 요청 |
| 해제 대기 | 해제를 요청했지만 기기에 아직 유효한 키가 남아 있을 수 있음 | 차지 | 해제 코드 입력 |
| 만료됨 | 기한이 지났는데 갱신되지 않음 | 차지 | 갱신하거나 바로 삭제(이동 아님) |

- **해제 대기 → 해제 완료(목록에서 사라짐):** 다음 중 하나가 일어나면 좌석이 빈다.
  - 기기가 온라인으로 갱신하다 해제 신호를 받음(SDK가 키를 지움).
  - SDK의 해제 기능으로 나온 **해제 코드**를 포털에 입력함.
  - 그 키의 마지막 기한이 지남.
  - 관리자가 강제로 해제함(고장·분실 PC).
- **만료됨**은 자동으로 지워지지 않는다. 사용자가 바로 삭제할 수 있고, 이 삭제와 그 자리에 새로 만드는 키는 월 이동 상한에 넣지 않는다.
- 해제 완료·삭제된 키는 키 기록 탭에 남는다.

**월 이동 상한**

- 한 번 이상 활성화된 좌석이 **사용 중 상태에서 해제돼** 비었고, 그 자리에 새 키를 만들면 **이동**이다.
- 이동은 달마다 상한(체험 1, 연장·계약 기본 2, 관리자가 조정)까지다.
- 상한에 도달하면 **새 키 만들기만 막는다.** 해제 요청과 삭제는 언제든 된다.
- 처음 좌석을 채우는 키, 미활성·만료됨 키를 지운 자리에 만드는 키는 이동이 아니다.
- 관리자는 예외로 상한을 풀 수 있다.

### 4.7 브라우저 승인으로 연결 (2026-10-17 결정)

키를 복사하지 않고 연결하는 방법. 기기가 짧은 코드를 보여주고, 사람이 포털에서 승인하면 기기가 활성화된 키를 받는다(TV·CLI 로그인과 같은 방식).

1. SDK가 코어의 활성화 요청(대상: 앱 ID 또는 PC 해시)을 `POST /sdk/v1/pairing`으로 보낸다. 키는 필요 없다.
   서버는 비밀 기기 코드와 사람이 입력할 연결 코드(`XXXX-XXXX`), 승인 주소를 돌려준다. 코드는 10분 동안 한 번만 쓸 수 있다.
2. 사람은 포털의 승인 주소(`/activate`)에 로그인해 코드를 넣는다. 화면에는 대상(앱 ID, 또는 PC 해시 앞 8자리)과 요청 시각이 나온다.
3. 조직의 **소유자·관리자**가 체험·계약을 고르고, **새 키를 만들거나(유효기간 선택) 기존 미활성 키를 골라** 승인한다.
   좌석 한도, 월 이동 상한, 체험 1회, 앱 ID 한 계약 규칙은 일반 활성화와 같다. 거절할 수도 있다.
4. SDK는 기기 코드로 `POST /sdk/v1/pairing/token`을 몇 초마다 확인하고, 승인되면 그 대상에 활성화된 키를 받아 저장한다.
5. 키 없이 시작한 앱도 저장소에서 이 앱·PC에 활성화된 키를 찾아 쓴다. 그래서 같은 PC의 다른 언어 앱도 한 번의 연결로 함께 쓴다.

- 추가로 받는 정보는 없다(컴퓨터 이름 등은 보내지 않음). 연결 요청은 만료 1시간 뒤 지운다(승인 기록은 키 활성화 기록과 감사 기록으로 남는다).
- 콘솔 명령(Python): `python -m fisica_sdk license pair|status|import|code|release`. 단일 실행 파일은 나중에 필요하면 만든다.
- 인터넷이 없는 기기는 지금의 활성화 코드(4.5)를 그대로 쓴다.
- 구현(2026-10-17): 포털 서버·`/activate` 페이지, Python(`Entitlement.pair`, `FisicaSDK.pair_device`, 콘솔 명령),
  C#(`PairAsync`)·Swift(`pair`/`pairNow`)·Kotlin(`pair`)·Dart(`pair`). 저장된 키는 래퍼가 만들어질 때 읽는다.

## 5. 키(토큰) 형식

기존 `FSE1` 형식과 Ed25519 서명은 그대로 두고 payload에 필드를 더한다. 지금의 코어는 모르는 필드를 무시하므로 서버를 먼저 바꿔도 된다.

| 필드 | 뜻 |
|---|---|
| `key` | 키(좌석) ID |
| `bind_type` | `app` 또는 `pc`. 미활성 키에는 없다 |
| `bind` | 앱 ID 또는 PC 해시. 미활성 키에는 없다 |
| `key_until` | 키 기한(Unix 초). 없으면 만료 없음 |
| `full_until` | 계약의 전체 모드 종료(Unix 초). 체험은 승인+체험 기간(기본 14일), 연장은 승인 기간 끝, 계약은 종료일+30일 |
| `features` | 전체 모드에서 여는 기능(쉼표 구분). 없으면 2.2의 전체 목록 |
| `track` | `trial` / `extension` / `contract` |

- 기존 필드(`verified_at`, `refresh_by`, `contract_*`, `revoked_at`, `grants`, `kind`)는 유지한다. `kind`는 지금 코어가 `basic`/`special`만 받으므로 체험·연장은 `basic`, 상업 계약은 `special`로 둔다.
- 키 해제는 그 키의 다음 갱신에서 `revoked_at`으로 서명된다(계약 폐기와 같은 표시).
- `full_until`이나 `bind`가 없는 키는 새 코어에서 기본 모드다. 아직 배포된 패키지가 없어 마이그레이션은 필요 없다.

서버 API:

| API | 본문 | 하는 일 |
|---|---|---|
| `POST /sdk/v1/entitlement/activate` (Bearer 미활성 키) | `{"bind_type":"app"\|"pc","bind":"…"}` | 키를 묶고 묶인 키를 돌려준다. 같은 대상이면 다시 돌려주고, 다른 대상이면 거절 |
| `POST /sdk/v1/entitlement/refresh` (Bearer 키) | `{}` | 지금처럼 다시 서명. 키 기한 연장, 해제·폐기 반영 |
| 포털: 활성화 코드 입력 | 활성화 코드 | 오프라인 활성화용 묶인 키 파일 |
| 포털: 갱신 파일 | — | 같은 키의 기한을 연장한 파일 |
| 포털: 해제 코드 입력 | 해제 코드 | 해제 대기 키를 해제 완료로 |

코드와 해시 형식(서버 구현 2026-10-16, 코어가 같은 규칙을 따른다):

- **활성화 코드:** `FAC1.<base64url({"k":키ID,"t":"app"|"pc","b":대상})>.<검사값>`. 검사값은 `FAC1.<본문>`의 SHA-256 앞 8자(16진수). 오타 확인용이다.
- **해제 코드:** `FRC1.<본문>.<검사값>`. 검사값은 `fisica-release-code-v1|FRC1.<본문>`의 SHA-256 앞 8자. 코어가 키를 지운 뒤에만 만든다. 규칙이 코어 안에 있어 억지 수준의 보호다(7절).
- **PC 해시:** `SHA-256("fisica-pc-v1:" + PC 고유값)`의 16진수 64자. 서버는 64자 16진수인지만 확인한다.
- **앱 ID:** 역도메인 형식(`[A-Za-z0-9][A-Za-z0-9_-]*(\.[A-Za-z0-9_-]+)+`, 최대 128자). 끝의 `.debug`·`.dev`는 같은 앱으로 본다.
- 갱신 응답에서 해제 대기 키는 `revoked_at`이 서명되고, 서버는 그 키를 해제 완료(`device`)로 기록한다.

## 6. 앱 ID와 PC 해시

| 플랫폼 | 묶는 대상 | 읽는 곳 |
|---|---|---|
| iOS·macOS 앱 (Swift, Flutter) | 번들 ID | 코어가 `CFBundleGetMainBundle`로 직접 |
| Android (Kotlin, Flutter) | 패키지명 | 코어가 `/proc/self/cmdline`으로 직접 |
| Windows (C#, Flutter, Python) | PC 해시 | 코어가 `MachineGuid`(레지스트리)로 직접 |
| macOS의 Python·C#·C/C++ (앱 번들이 아님) | PC 해시 | 코어가 `IOPlatformUUID`로 직접 |
| Linux(향후) | PC 해시 | `/etc/machine-id` |

- 대상은 래퍼가 넘겨주지 않는다. 래퍼는 소스가 공개돼 고칠 수 있다.
- **PC 해시는 모든 계정에서 같은 값**이다(D-PC). PC 고유값을 고정된 접두어와 함께 SHA-256으로 해시한 값이고 원래 값은 보내지 않는다. 같은 PC는 회사가 달라도 같은 해시라서 "PC당 체험 1회"를 지킬 수 있다.
- 모바일 앱의 좌석은 **앱 하나**다. 같은 앱을 설치한 최종 사용자 기기 수는 세지 않는다.
- 디버그 빌드 접미사(`.debug`, `.dev`)는 같은 앱으로 본다.

## 7. 꼼수 방지

| 위협 | 대응 | 남는 위험 |
|---|---|---|
| 계정을 새로 만들어 체험 반복 | 계정·회사·사업자등록번호당 1회. 활성화할 때 앱 ID·PC 해시당 1회 | 새 앱 ID와 새 PC를 함께 쓰는 경우 |
| 키 위조 | Ed25519 서명, 비밀키는 포털 서버에만. 고객 빌드는 production 공개키만 | 비밀키 유출 |
| 키를 다른 앱·PC에 복사 | 키가 처음 활성화한 앱 ID·PC에 묶임 → 기본 모드 | 같은 PC 해시가 나오는 복제 가상 머신 |
| 다른 앱의 앱 ID 흉내 | Android: 프로세스 이름(매니페스트 `android:process`로 바꿀 수 있음)을 그 패키지의 설치 APK(`/data/app/…/<패키지>-…/base.apk`)가 이 프로세스에 올라와 있을 때만 인정(2026-10-17) | macOS: 아무 `.app`이나 번들 ID를 정할 수 있다. 막으려면 키에 Apple 팀 ID를 넣고 코어가 앱 서명과 비교해야 하며, 포털에 팀 ID 입력과 서명 안 된 개발 빌드 처리가 필요하다(기록만, 미구현) |
| 좌석을 돌려가며 쓰기 | 월 이동 상한, 모든 활성화·해제를 관리자 기록에 남김 | 상한 안의 이동 |
| 오프라인 기기의 키를 해제 요청하고 새 키를 다른 PC에 | 해제 대기 키는 해제 코드나 기한 만료 전까지 좌석을 차지 | "만료 없음" 키는 관리자 개입이 필요 |
| 해제 코드 위조 | 코드는 SDK가 키를 지운 뒤 만든다. 코어 안 규칙으로 생성. 온라인 기기는 해제할 때 키로 서버에 직접 알려(`/sdk/v1/entitlement/release`, 2026-10-17) 코드가 필요 없다 | 오프라인 코드는 코어를 역분석하면 만들 수 있음(억지 수준). 비워진 자리에 새 키를 만드는 것은 월 이동 상한에 걸린다 |
| 해제 전에 저장해 둔 상태를 되살리기 | 온라인이면 다음 갱신에서 해제된 키로 판정돼 기본 모드 | 오프라인이면 키 기한까지 쓸 수 있음. 막으려면 기기 인증(W7) |
| 같은 앱 ID로 다른 회사가 재사용·재판매 | 약관으로 금지. 같은 앱 ID는 한 계약에서만 활성화 | 다른 계약끼리의 앱 ID 중복은 관리자 확인 |
| 기기 시계를 되돌려 기한 연장 | 코어가 지금까지 본 가장 늦은 시각을 저장해 감지(D8). 키의 `verified_at`보다 이른 시계는 기본 모드 | 저장 상태를 지우면 감지 못 함 |
| 래퍼가 코어에 넘기는 시각을 조작 | 고객 빌드의 코어는 시스템 시계를 직접 읽고, 호스트 시각은 더 늦을 때만 쓴다. 기본 모드 초당 1장과 세션의 전체 모드 끝도 코어 시계로 잰다(D-시계주입, 2026-10-17) | 시스템 시계 자체를 바꾸는 것은 위 시계 되돌림과 같다 |
| 만료 후 시계를 기한 안에 묶어 두기 | 시계 되돌림 감지(D8), 짧은 키 기한(관리자가 최대 기한 지정) | 상태 삭제와 시계 조작을 반복하면 막지 못함. 확실히 막으려면 기기 인증(W7) |
| 래퍼를 고쳐 제한 우회 | 판정·제한·대상 읽기는 비공개 코어 안 | 없음 |
| 코어 바이너리 패치·역분석 | 심볼 제거·숨김(적용 중), 약관에 역설계 금지(D9) | 비용만 높일 뿐 막지 못함 |
| SDK 없이 프로토콜 직접 구현 | PyPI 1.0.x 삭제(W6), 장기적으로 펌웨어 기기 인증(W7) | 이미 받은 MIT 사본, 평문 프로토콜 |
| 복제 기기에 정품 SDK 사용 | 장기: 펌웨어 기기 인증(W7) | 현재 SDK는 기기 진위를 모름 |
| 계약 폐기 후 오프라인으로 계속 사용 | 다음 갱신에서 반영. 계약 종료일이 지나면 오프라인에서도 기본 모드 | 폐기~키 기한 사이 오프라인 사용 |
| 테스트 키로 서명한 키 사용 | 고객 빌드에는 테스트 공개키가 없다(적용 중) | 없음 |

## 8. 개인정보와 사용 추적 원칙

- **SDK는 측정 횟수, 사용 시각, 측정 데이터를 보내지 않는다.**
- 서버가 저장하는 것: 신청과 발급 기록(계정, 회사, 신청 내용), **키별 묶인 대상(앱 ID 또는 PC 해시)과 활성화·갱신·해제 시각**, 체험 사용 여부.
  - 이것으로 좌석·설치 수(앱·PC)는 알 수 있다. 외부 사례 조사(16곳 중 8곳이 기기·설치 수나 사용량을 집계)에 따른 결정이다(D12).
  - 갱신 시각은 키 기한 계산용이며, 마지막 실제 사용 시각이 아니다(오프라인 사용은 보이지 않는다).
- 갱신 요청 본문은 지금처럼 `{}`만 받는다. 활성화 요청만 대상(앱 ID·PC 해시)을 싣는다.
- PC 해시는 원래 PC 고유값이 아니라 해시만 받는다. 개인정보 처리방침에 "기기 식별용 해시"로 고지한다.
- 상업 체험 담당자 연락처는 개인정보 수집·이용 동의(항목·목적·보유기간)를 받는다. 보유기간 예: 체험 종료 후 1년 또는 계약 종료 후 5년.
- 코어가 기기에 저장하는 것은 서명된 키와 시계 되돌림 감지용 최대 시각뿐이다.

- Fisica 개인 계정 가입에 본인 확인(휴대폰 등)이 있는지에 따라 체험 반복 방지의 강도가 달라진다.
- 상업 고객이 같은 앱 ID로 여러 고객사에 납품(SI)하는 경우의 계약 단위는 영업 정책으로 정한다.
- 월 이동 상한의 "달"은 한국 시간 기준 달력 월로 계산한다(구현 기본값).
