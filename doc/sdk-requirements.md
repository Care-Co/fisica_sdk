# Fisica Scale SDK 요구사항과 Windows 우선 지원

이 문서는 사용자와 확정한 SDK 제품 요구사항이다. 구현 완료와 실기기 검증
완료를 구분하며, 아직 확인하지 않은 펌웨어 정보를 지원 보증으로 사용하지 않는다.

현재 적용 정책은 2026-10-17 기준이다. 사용권·배포·라이선스에 관한 내용은 이전 기술을 대체한다.
바뀐 부분은 "라이선스·사용권·SDK 키" 절과 문서 끝의 개정 요약, [정책 이력](policy-history.md),
[라이선스 개편안](licensing-plan.md)에 있다.

## 목적과 변경 범위

- 파트너가 Fisica Scale을 자체 서비스·앱·하드웨어와 결합할 수 있게 한다.
- 기존 `fisica_sdk` 기능 전체를 Windows에서 우선 제공한다. 가능한 한 빨리
  제공하되 테스트하지 않은 기기 동작을 완료로 표시하지 않는다.
- 기기 펌웨어는 변경하지 않는다. 서버는 체험·연장·계약 신청과 SDK 키 발급·활성화·갱신·해제를 맡는다.
  서버는 개발자 포털(https://developer.fisicahealthcare.com)로 구현했다([entitlement-api.yaml](entitlement-api.yaml)).
- 현재 특정 파트너나 내부 프로젝트는 없다.

## 지원 환경

| 환경 | 연결 | 우선순위 |
|---|---|---|
| Windows 10/11, Intel/AMD x64 | BLE와 USB 모두 | 최초 지원 대상 |
| macOS | BLE와 USB 모두 | 후속 지원 |
| Android | BLE 우선, USB 추후 검토 | 후속 지원 |
| iOS | BLE 우선, USB 추후 검토 | 후속 지원 |
| Windows ARM64 | BLE/USB 계약, ARM64 바이너리 | 지원 구성 추가, 실기기 검증 대기 |
| 기타 OS·하드웨어 | 추후 결정 | 확장 대상 |
| Wi-Fi 연결 | 향후 개발 | 최초 지원 범위 제외 |

macOS·Android·iOS 사이의 출시 순서, 최소 OS 버전, 세부 기종 및 임베디드
제약은 아직 미정이다. Mac으로 검증할 수 있다는 사실이 Windows 검증을 대체하지 않는다.
기존 Wi-Fi 설정 명령의 호환성 유지와 향후 Wi-Fi Transport 구현은 서로 다른 범위다.

## 기능과 공개 데이터

- 검색·연결·해제, 측정 시작·종료, 기간 지정, 실시간 콜백, 프레임·세션 관리.
- 기존 체중·족저압 분석, 시각화(이미지 렌더링, Python 선택 설치), 보고서 조회·내보내기. SDK 자체 GUI는 3.0.0에서 뺐다.
- 기존 명령·기기 설정·영점·보정 기능은 일반 파트너도 사용 가능(기본 모드).
- 기기가 보낸 원본 패킷, 해석한 원본 센서 배열, 가공 배열을 **전체 모드**에서 제공한다.
  체중·발 길이·폭 분석 결과와 초당 1장의 표시용 격자는 기본 모드에서도 제공한다.
- 파트너의 자체 분석을 허용한다(원본 데이터는 전체 모드). 기기 설정 및 보정 기능은 모드와 상관없이 잠그지 않는다.
- 기존 API를 유지한다. 변경이 필요하면 래퍼 버전별 대체 API·deprecated 시점·제거
  시점을 안내한다. 공개 데이터 필드 추가는 기존 필드를 제거하거나 의미를 바꾸지 않는다.
- 원본/가공 센서값은 보정된 kPa로 표시하지 않는다. 배터리 placeholder와 실제
  측정값을 구분하고, 기존 nominal 1cm 기반 발 치수·안정화 정책의 한계를 설명한다.

## 목표 아키텍처

- 단일 네이티브 코어가 프로토콜·프레이밍·측정/분석 규칙·기기 상태 전이·공통
  에러 코드와 결과 계약을 담당한다.
- 외부 경계는 C ABI다. 코어 소스는 비공개이고 OS 통신 라이브러리에 의존하지 않는다.
- 코어는 바이트/연결 이벤트/주입된 시간을 받아 결과 이벤트·보낼 바이트를 반환한다.
  실제 BLE·USB·향후 통신은 플랫폼 Transport가 담당한다.
- Python·Flutter 등 래퍼는 언어별 자료형·메모리·비동기 API를 제공한다.
- 파트너 Transport 주입과 하드웨어 없는 Mock/Replay 개발을 지원한다.
- SDK·코어·ABI·래퍼 버전을 분리한다. 래퍼는 독립적으로 확장·버전 관리 가능해야 한다.
- 플랫폼·아키텍처·코어 버전이 같으면 모든 회사가 동일한 바이너리를 쓴다. 회사·계약·좌석은
  서버가 서명한 SDK 키로 런타임에 주입하고, 서명 검증·대상 확인·모드 판정·기능 제한은 코어가 한다.
- 모든 구현된 바인딩은 동일한 골든 입력/기대 결과로 검증한다.
- 향후 SwiftPM/XCFramework, AAR, NuGet, npm, C 정적 라이브러리 배포는 플랫폼 선정 후 진행한다.

현재 C++17 코어를 유지한다. Rust 이전이나 MCU를 위한 C 중심 재작성은 이번
Windows 작업의 범위가 아니며, 향후 대상 하드웨어 제약에 따라 별도 검토한다.

## 기기 호환성

- 현재 판매·외부 유통된 Scale 전체가 지원 목표다.
- 양산 예정 펌웨어 기준은 사용자 확인에 따라 `2.0.1`이다. 현재 연결된 테스트
  기기는 임시 `2.0.2` 계열이며 실제 조회 문자열은 `2.0.2-RC1`이다.
  임시 기기의 검증 결과를 `2.0.1` 양산 펌웨어 검증으로 간주하지 않는다.
- 기존 펌웨어 버전 조회 명령을 사용한다. 응답이 없거나 조회가 거절돼도 경고 후
  연결을 유지한다. 새로운 협상·CRC·인증 기능을 펌웨어에 추가하지 않는다.
- 미검증 펌웨어는 `FIRMWARE_UNVERIFIED` 경고와 조회 정보를 제공한 뒤 바로 사용을
  계속한다. 파트너 앱이 경고를 표시/기록할 수 있고 별도 허용 설정은 필요 없다.
- `verified_versions`에는 실제 검증한 버전만 등록한다. 현재 목록은 비어 있다.
- 펌웨어 경고 허용과 코어 ABI의 안전성은 별개다. 호출할 수 없는 ABI는 실행 전에 거부한다.
- 재연결은 원래 선택한 기기로 제한한다. USB serial number가 있으면 포트 번호 변경을
  추적하고, 없으면 원래 포트를 사용한다. 다른 Scale로 세션을 자동 전환하지 않는다.
  같은 식별 정보를 가진 후보가 여러 대면 자동 복구하지 않는다. USB 어댑터의
  serial number가 제품별로 고유한지는 별도 확인 대상이며, 기기 인증을 의미하지 않는다.
- SDK가 측정 모드를 요청한 경우 명시적 disconnect에서 모드를 해제하고 I/O를 닫는다.

## 라이선스·사용권·SDK 키

[LICENSE](../LICENSE) 2.0(2026-10-17 확정)과 [라이선스 개편안](licensing-plan.md)이 기준이다.

기본 SDK 사용권 = 기본 모드:

- 정품 Fisica 장비 구매에 포함된다. 날짜 기반 만료가 없다. 상업 사용도 등록·SDK 키·서명 계약 없이 쓸 수 있다.
- 연결·측정·기기 설정·영점·보정·체중·발 길이와 폭·초당 1장의 미리보기·보고서 요약을 제공하며,
  이 기능은 키·계약 상태로 막지 않는다.
- 공개 래퍼의 수정과 자체 앱에 포함한 배포를 허용한다. SDK 자체의 독립 판매·단독 재배포는 포함하지 않는다.

전체 모드:

- 원본 패킷·원본/가공 격자, 매 프레임, 전체 보고서 내보내기, 향후 고급 분석.
- 체험(누구나 1회, 담당자 승인), 비상업 무료 연장(교육·연구·공공, 관리자 결정), 상업 계약 중 하나의
  SDK 키가 그 앱·PC에 활성화돼 있고, 키 기한과 전체 모드 기간 안일 때만 동작한다.
- 기간·좌석 수·월 이동 상한·유예(계약 종료 후 30일)·키 최대 기한은 승인·계약과 개발자 포털에 게시한 조건을 따른다.
- 체험·연장·계약이 끝나면 기본 모드로 돌아간다. 기본 사용권, 장비 소유권, 장비 등록은 그대로이고,
  적법하게 공급된 앱의 최종 사용자는 기본 모드를 계속 쓴다.

별도 계약:

- OEM 통합, 하드웨어 리브랜딩, SDK 재판매, 정품 장비 외 사용 등 약관의 예외에만 필요하다.
  상업 계약에 해당 권한(`grants`)으로 넣을 수 있다.
- 유료 지원·클라우드·분석 API는 실제 상품이 있을 때만 별도 계약으로 관리한다.

SDK 키([entitlement.md](entitlement.md)):

- 키 하나가 좌석 하나다. 처음 쓸 때 이 앱의 ID(모바일·macOS 앱) 또는 이 PC의 해시(Windows·스크립트)에 활성화되고,
  그 대상에서만 전체 모드가 된다. 대상은 코어가 직접 읽는다.
- 온라인 활성화·갱신과 오프라인 활성화 코드·키 파일·해제 코드를 모두 지원한다. 인터넷이 없는 PC도 설정할 수 있다.
- 통신 실패는 만료·해제가 아니다. 시계를 1시간 넘게 되돌리면 기본 모드다.
- 서명된 키와 지금까지 본 가장 늦은 시각을 오프라인 판정을 위해 기기에 저장한다. SDK 사용 이력이 아니다.

SDK 사용 추적 제외(2026-10-14):

- SDK 사용 기록을 수집·보관·보고하지 않는다. 회사·계약별 사용 여부, 마지막 실제 사용일시,
  계약 만료·폐기 후 사용 여부를 기록하거나 보고하지 않는다.
- 측정 횟수, API 호출 횟수, 앱·설치·기기별 사용 추적도 하지 않는다.
- 체험·연장·계약 신청, 약관 수락, SDK 키 활성화·갱신·해제, 오프라인 서명 검증은 유지한다.
  서버는 키마다 활성화 대상(앱 ID 또는 PC 해시)과 활성화·갱신·해제 시각을 저장한다(좌석 관리용).
- 마지막 서버 갱신 시각은 마지막 실제 SDK 사용일시가 아니다. 서버의 활성화·갱신 기록으로 실제 사용 여부나
  계약 준수를 알 수 있다고 보지 않는다.
- 파트너 앱이 자체 서비스 목적으로 측정 데이터·보고서를 저장하는 기능은 유지한다. SDK 사용 추적과 별개다.
- 2026-10-13 정책으로 만들었던 사용 기록 코드는 2026-10-14에 제거했다([entitlement.md](entitlement.md)의 "구현 상태").
- 측정 장비(Scale) 잠금은 추가하지 않는다. SDK 키의 활성화 대상(앱 ID·PC 해시)은 좌석 관리용이며
  설치·최종 사용자 기기별 추적 단위가 아니다(모바일 앱은 설치 수와 상관없이 앱 하나가 좌석 하나).

## 문서와 실제 데이터의 불일치

참고 원본은 `케어앤코-Fisica-Scale.pdf`(16쪽)와
`250310_케어앤코-Fisica-Scale.pdf`(2025-03-10 보완, 1쪽)다.

| 항목 | 문서/기존 구현 | 이번 처리·검증 범위 |
|---|---|---|
| 측정 크기 | 본문 16쪽은 644 bytes, 보완은 count index를 언급. SDK와 저장 샘플은 645 bytes | SDK의 645-byte 계약 유지. 644-byte 기기 지원 여부는 실기기에서 확인 |
| 첫 구분자 | 기존 스트림 코어는 638/639, 저장 샘플은 639/640 | 두 645-byte 레이아웃을 공통 코어에서 프레이밍. 기존 수치 fixture 유지 |
| 연속 측정 | 본문 12쪽·보완은 USB 모드에서만 가능. 기존 Serial도 BLE 모드를 설정 | Serial 시작을 USB 모드로 수정. 기존 BLE 측정 동작은 펌웨어 확인 전 유지하며 실기기 검증 대기 |
| 단일 측정 | 보완에서 BLE 사용자 ID 항목 제거 | 기존 명령 계약을 무검증으로 변경하지 않음. 실제 펌웨어에 맞는 명령은 후속 확인 |
| 펌웨어 응답 | 본문 11쪽은 가변 길이, 기존 파서는 고정 8 bytes만 처리 | 코어의 가변 query 응답 프레이밍/내용 추출 및 연결 시 조회 추가 |
| 오류 | 본문 15쪽은 기기 오류 1~9 | 기존 응답의 RET·data·payload 노출. 코어/Transport 예외 코드는 보존. C ABI 세션에서 ACK·timeout 및 16-bit 기기 오류 코드 처리 |

회귀 fixture는 알고리즘 결과의 재현성을 확인하는 자료다. 문서의 정확성이나
양산 예정 펌웨어 `2.0.1`의 지원을 실기기로 입증한 자료가 아니다. 단독 `decode_packet`은
기존 decode-only 계약을 유지하며, 수신 스트림 구분자 검증은 `next_packet`이 담당한다.

[타사 앱 적용 가이드](partner-quickstart.md)를 따른다. 모바일 바이너리와 Flutter BLE/desktop USB
어댑터, 권한 설정을 포함한 최소 앱은 제공한다. 실제 Windows·Android/iOS·ARM64 기기의
연결·측정 결과와 양산 BLE 경로는 검증 전이며 구현과 실기기 검증을 구분한다.

## Windows 완료 기준과 검증 절차

1. Windows x64 MSVC 빌드와 Python 설치 matrix 통과.
2. 바이너리 휠의 라이선스·아키텍처·소스/디버그 제외 감사 통과, sdist 차단.
3. 소스 checkout 밖에서 휠 설치 후 offline Mock 측정·분석·원본 조회·보정 명령·deprecated 검증.
4. 시각화 extra 설치 후 모든 렌더 모드의 이미지 검증.
5. 실물 Scale에서 USB·BLE 검색/연결, 버전 조회, 시작·종료·기간 측정·콜백·원본·
   분석·보고서·시각화·끊김/동일 기기 복구를 검증.
6. 영점·보정은 빈 기기·기준 무게·복구 방법이 준비된 상태에서 별도로 수행.
   자동 smoke에 물리 기기 보정이나 설정 변경을 넣지 않는다.
7. 회사가 달라도 바이너리 해시가 같고 코어에 회사·계약·배포 ID가 없음을 확인. 운영 서명 키로 빌드했는지 확인.

Mock 및 Wine 검증은 실기기/실제 Windows 드라이버·Bluetooth 검증을 대체하지 않는다.
현재 Mac 실물 테스트가 가능한 것으로 확인됐지만, 실제 연결이 발견돼야 기기 검증을 진행한다.
명령/입력 바이트를 바꾸기 전 문서·저장 샘플·실기기 결과를 함께 비교한다.

이번 연결 기기에서 조회한 `2.0.2-RC1`은 Mac USB 측정 시작/종료, 모드 해제 응답과
645-byte 수신·원본 내보내기를 확인했다. 이 결과를 양산 `2.0.1` 또는 Windows/BLE
검증 결과로 확장하지 않는다. 영점·보정·펌웨어 변경은 수행하지 않았다.

빌드·검증 명령 및 최신 검증 범위는 [Windows 배포 안내](windows-distribution.md),
ABI·래퍼 확장 방법은 [네이티브 SDK 안내](native-sdk.md)를 참조한다.


## 공통 세션 코어 개선 (SDK/Python 2.2.0, core 1.2.0, ABI 1.2)

측정 상태 전이와 모드/시작/종료/해제 명령 순서, ACK 일치·거절·timeout,
펌웨어 조회 timeout, 기간 종료와 재연결 후 측정 재개 판단은 공통 코어에 있다.
Python/Flutter는 같은 세션 C ABI와 공통 벡터를 사용한다. 기존 Python 메서드와
Windows x64 바이너리 배포 경로는 유지한다. 코어 소스는 배포하지 않는다.

명령을 보냈다는 사실만으로 성공 처리하지 않는다. 명령 timeout이면 코어는
결과가 불확실한 FAULT로 전환하고 자동 재전송을 하지 않는다. `wait()`에서 SDK
오류 코드, 기기 거절이면 별도 `device_code`도 확인할 수 있다. 이 경우 disconnect는
PC 자원을 닫되 모드 해제를 확인할 수 없다는 오류를 반환할 수 있다. 조회 timeout은
기존 미검증 경고 후 사용 지속 정책을 유지한다.

2026-10-13 Mac USB 실기기 `2.0.2-RC1`에서 시작/종료 ACK, 3초 기간 종료,
동일 연결에서 재측정, 측정 중 disconnect, 645-byte 수신과 최종 모드 해제 ACK를 확인했다.
서버·펌웨어·영점·보정은 변경하지 않았다. 양산 `2.0.1`, 실제 Windows 드라이버,
BLE 및 물리 케이블 끊김/복구의 검증은 별도로 필요하다.

최종 검증 증거와 실행 한계는 [공통 세션 코어 검증 기록](session-core-verification.md)을 참조한다.
